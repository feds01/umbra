# Command line

The `umbra` command does without Go what the library does with it: it checks a
catalog of `.pii` files against a database, and prints the SQL of the masked views
for your migrations. The catalog can be written by hand, or generated by a Go
program, as in [Getting started](getting-started.md).

```text
umbra check [--postgres <url>] [--config <path>]
umbra views postgres [--replace] [--config <path>] [<table>...]
umbra views bigquery [--config <path>] [<table>...]
umbra version
```

## umbra.toml

Every command reads the nearest `umbra.toml`, at or above the working directory, or
the one named with `--config`. Paths in it are relative to the file. Unknown keys
are errors.

```toml
catalog = "catalog"                 # the .pii files, a directory per dataset

[policy]
reasons = ["person", "credential"]
bases = ["business_data"]

[[policy.maskers]]
term = "generalise=domain"
suffix = "domain"
kinds = ["text"]                    # text, uuid, inet or scalar
reason = "person"

[[policy.maskers]]
term = "pseudonymise"
suffix = "pseudonym"
kinds = ["text"]
reads = ["org_id"]

[postgres]
dataset = "postgres"                # catalog/postgres
tables = "public"                   # the schema of the tables, public if omitted
views = "masked"                    # the schema of the views
role = "analyst"                    # granted SELECT on each view
classification = "classification"   # also print the classification view, under this name
masks."generalise=domain" = { extract = "email" }
masks.pseudonymise = { hmac = { scope = "org_id", key = "SELECT key FROM private.pseudonym_key" } }

[bigquery]
dataset = "warehouse"               # catalog/warehouse
project = "acme"
tables = "events"                   # the dataset of the tables
views = "masked"                    # the dataset of the views
schemas = "schemas"                 # a `bq show --schema` file for each table: <table>.json
masks."generalise=domain" = { extract = "email" }
```

`[policy]` is [the policy](concepts.md#the-policy), except for its rules, which are Go
functions. A mask for a term the policy doesn't declare is an error. `views`, `tables`
and `role` are written into the SQL as given, so quote one that needs it, as in
`views = '"my-schema"'`. A mask is exactly one of:

| Mask | Shows |
|---|---|
| `{ extract = "email" }` or `"url"` | the domain of an address, or the host of a URL |
| `{ pattern = '<regex>' }` | what the regular expression's one group captures |
| `{ hmac = { scope, key } }` | a keyed pseudonym, in PostgreSQL only |

## Commands

### check

1. Loads the catalog against the policy, and reports every bad file, line and tag.
2. With `--postgres`, reads the database's schema and compares the `[postgres]`
   dataset with it.
3. When `[bigquery]` has `schemas`, compares the `[bigquery]` dataset with those files.

Prefer the `PG*` environment variables (`PGPASSWORD` and the rest) to a password in
the URL, which anyone on the machine can read in the process list. They fill in what
the URL leaves out. An error never shows the URL.

### views postgres

Prints the views of the named tables, or of every table of the dataset. With no table
named and `classification` set, it prints the classification view too. `--replace`
drops each view before creating it.

```sh
umbra views postgres --replace > migrations/0042_masked_views.sql
```

### views bigquery {#bigquery}

Prints one `CREATE OR REPLACE VIEW` for each table, over the schema file that
`bq show --schema` wrote for it:

```sh
bq show --schema --format=prettyjson acme:events.events > schemas/events.json
umbra views bigquery events
```

A missing file is an error that names this command.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | nothing was found |
| 1 | the catalog has problems: bad files, unclassified or stale columns, or a class that doesn't fit its type |
| 2 | umbra couldn't run: a bad command line, `umbra.toml` or policy, a database it couldn't reach, or output it couldn't write |

SQL goes to standard output, and problems and errors to standard error. A command
prints nothing unless it can render everything, so redirecting the output into a
migration never leaves one half-written. A flag after a table name, or a stray
argument to `check`, is a usage error, and so is output that can't be written.
